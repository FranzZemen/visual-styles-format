# visual-styles-format — intent

## Purpose

The file format behind Broken Stock's Visual Styles panel
(`broken-stock/doc/prd/visual-styles.prd.md`, D2, D9, D11, D12, D22; epic E2): the shape of
`src/styles/visual-styles.json`, its validation, and the generators that turn it into
`visual-styles.css` and the Tailwind theme block `visual-styles.theme.css`.

It is its own package because three different programs must produce **identical** output from the
same JSON:

| Consumer | Uses it to |
|---|---|
| `@franzzemen/visual-styles` (the Angular panel, in the browser) | validate edits, preview, resolve swatches, diff for the save list, hash the loaded file |
| `@franzzemen/visualstyles-app` (the local save server, plain Node) | validate a save, write the three files, hash for the stale-save check |
| broken-stock (`scripts/visual-styles-generate.mjs`, `src/styles/visual-styles.spec.ts`) | regenerate by hand; fail the test suite if the committed CSS is not what the JSON produces |

Inside the Angular library the save server would have had to install Angular to write a JSON file
(PRD v0.2.0 review, SE2). So the code is pure TypeScript with no Angular, no DOM and no Node APIs.
`contentHash` uses Web Crypto, which both browsers and Node provide.

## The file

```json
{"formatVersion": 1, "entries": [ {"name": "profit.text", "kind": "colour", "group": "Meaning",
  "description": "Profit text", "value": "#1b5e20", "legacyName": "--color-profit", "tailwind": true} ]}
```

Each entry has a `name`, a `kind` (`colour` or `number`), a `group` and a `description` (the last
two are for the panel only and never reach CSS), and **exactly one of** `value` or `follow`.
Optional: `unit` (numbers with their own value, required there), `background` (colours; the entry
its contrast is checked against, default `surface`), `chart` (an array of `{scope, selector,
property}` rules), `legacyName` (an existing custom property this entry takes over) and `tailwind`
(colours; also write it into the Tailwind theme). The full field table is in the README. Unknown
fields are refused at every level.

## Invariants

- **Every entry becomes `--vs-<name>`, dots turned into dashes** (`profit.text` → `--vs-profit-text`).
  Two names that collide after that change are refused (`duplicate-css-name`). Nothing else is ever
  emitted under `--vs-*`, and a `legacyName` may never start with `--vs-`.
- **A follow is a reference, never a copy.** `{"follow": {"target": "series-1"}}` generates
  `--vs-x: var(--vs-series-1);`, so the browser moves every follower when the leader changes, with
  no script. A follow with `opacity` (0–100, colours only) generates
  `color-mix(in srgb, var(--vs-series-1) 40%, transparent)`. Opacities along a chain multiply
  (`resolveEntry`). The target must exist and have the same kind, and loops are refused.
- **The grammar refuses; it never cleans (D22).** Colours are hex (`#rgb`, `#rgba`, `#rrggbb`,
  `#rrggbbaa`) or `rgb()`/`rgba()`/`hsl()`/`hsla()` with numbers only, range-checked. Keywords are
  refused, including `transparent` (write `#0000`), `currentColor` and `color-mix`. Numbers must be
  finite and not in exponent form, with a unit (`px`, `rem`, `em`, `%`, or an explicit `none`). Any
  string bound for CSS that contains `url(`, `;`, `{`, `}`, `\`, `/*`, `*/`, quotes, `<`, `>` or a
  control character is refused outright. Chart rules allow one scope class, class-only selectors
  (which may end in one element name from a fixed list — `text`, `tspan`, `path`, `rect` — because
  Highcharts colours some button, range-label and legend words only through an element selector),
  and a property from a per-kind allow-list. Pseudo-classes (`:hover`) and `!important` are not part
  of the format: a state Highcharts marks only with `:hover`, or colours with `!important`, stays in
  a hand-written structural sheet that reads the entry by variable.
  **Why:** the save server listens only on 127.0.0.1, but any website open in Franz's browser could
  still try to post a "colour" that is really CSS (a `url(` that leaks data, a `}` that opens a new
  rule). If it were accepted, it would be committed and shipped. Repairing such input would mean
  guessing what was meant. Refusing it is simple and can be checked.
- **Validation returns every error and never fixes anything.** Each error is
  `{path, entry?, code, message}`. Both generators throw `VisualStylesInvalidError` rather than emit
  CSS from a file that failed.
- **Output is deterministic.** The same file gives the same bytes, whatever the order of entries or
  fields. The order is:
  1. the version stamp line:
     `/* Generated by @franzzemen/visual-styles-format <version> (format 1) from visual-styles.json. Do not edit. */`
  2. one `:root` block of `--vs-*` variables, sorted by CSS name;
  3. a second `:root` block of legacy aliases (`--color-profit: var(--vs-profit-text);`), sorted by
     legacy name;
  4. chart rules `.<scope> <selector> { <property>: var(--vs-…); }`, sorted by scope, then selector,
     then property.

  Lines end in `\n` and nothing comes from the environment. broken-stock's test reads the stamp back
  (`readGeneratorStamp`) and fails if it is not the installed version, so a version bump here means
  regenerating broken-stock's files.
- **The stamped version is the published version.** `src/project/version.ts` holds it because the
  browser cannot read `package.json`. The npm `version` script (`scripts/stamp-version.mjs`) rewrites
  it during `bs.patch`/`bs.minor`/`bs.major`, and a test fails if it disagrees with `package.json`.

## Tailwind: `@theme inline`

`generateTailwindTheme` writes `@theme inline { --color-profit: var(--vs-profit-text); … }` for
`tailwind: true` entries. With `inline`, Tailwind writes the variable into each utility
(`.text-profit { color: var(--vs-profit-text) }`), so a live edit of `--vs-profit-text` repaints the
Tailwind classes, every `var(--color-profit)` use and the charts together.

**Tailwind still writes its own copy of each name.** In broken-stock's build (tailwindcss 4.3.3,
checked in `dist/…/styles-*.css`) Tailwind's `@layer theme` still contains
`--color-profit: var(--vs-profit)`. That is a second definition of the same name, with the same
value. It does no harm, because the generated alias sits outside any cascade layer and so always
wins over the layered copy, and an edit to the `--vs-*` variable reaches both. It is the reason the
panel edits only `--vs-*` names and never `--color-*` ones. (E2's first measurement, against a bare
Tailwind compile, said no copy is written. E3 found the copy in the real build.)

The Tailwind name is the entry's `legacyName` when that starts with `--color-`, otherwise
`--color-` plus the CSS name without `--vs-`. Only colours can be Tailwind entries; fonts and
spacing would need a format change.

## Boundaries

- In: an `unknown` value or JSON text. Out: errors, generated text, resolved values, diffs, hashes.
  No I/O: callers read and write the files.
- Not here: where files live, the HTTP protocol (visualstyles-app), contrast or colour-blind checks
  and pick mode (the panel), which charts are converted (broken-stock).
- Dark only and no gradients: a light theme or gradients would change the JSON shape
  (`formatVersion`).

## Guidance for agents

- Never loosen the grammar to accept a value that "looks harmless". Add a precise new form with
  tests for both acceptance and refusal.
- A change to generated output is a change to broken-stock's committed CSS. Release, bump
  broken-stock, run `node scripts/visual-styles-generate.mjs` there, and commit the regenerated
  files, or its agreement test fails.
- Chart rules emit no `!important`. Rules that need `:hover` or `!important` cannot be written in
  the format today (PRD F12) and live in broken-stock's structural `*-styled.css` sheets.
- Nothing in the format marks an entry as "text" or names a chart pane, so the panel's checks have
  to infer both (PRD F14, F15). Adding a field means a new optional field plus validation, and
  `formatVisualStyles` must place it in its fixed field order.
- `contentHash` is async. Hash the parsed file, not the raw bytes: a whitespace-only hand edit does
  not make a save stale.
